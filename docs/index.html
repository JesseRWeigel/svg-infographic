A layout engine where the model writes data and a solver writes geometry

The model produces a typed spec: a title, some bars, some cards, some steps. It never picks a coordinate. A difference-constraint solver assigns every position from measured text widths, and if the constraints cannot all hold the engine refuses and names the conflict rather than emitting something broken.

Why SVG text is the hard part

SVG has no text layout. You write <text x="10" y="20">hello</text> and the renderer decides how wide that is. Nothing in the file says. So an engine that wants to promise a label fits its box has to compute the same number the renderer will, which means reading the font.

This engine parses the TrueType tables directly: cmap for character to glyph, hmtx for each glyph's advance width, head for the em scale. Summing advances gives the width. The tempting shortcut, len(text) * constant, is wrong by up to 80 percent on ten-character strings, which the first figure below shows at full size.

Three things the browser changed about this engine

All three were found by measuring the published page, not by reading the code. Each one is a case where the engine was correct about the font and wrong about the renderer.

what was wrongerrorthe fix
Chromium rounded every glyph advance to a whole pixel, so a 45-character line rendered wider than the sum of its advances12.05 px text-rendering: geometricPrecision, after which the two agree to 0.014 px
font-kerning="none" as an SVG attribute was ignored; computed style came back auton/a set it in a style attribute, where it takes effect
the box the renderer reports covers the font's full line metrics, not the typographic ascender and descender, so glyphs sat outside their containers518 elements reserve the union of the hhea, typographic and windows metrics, plus the ink of the glyphs being set, plus one pixel for the renderer's rounding

A fourth was found by attacking the verify script rather than the engine: inverting one rounding function so measured widths rounded down instead of up produced containers a hundredth of a pixel narrower than their content, and the checker's tolerance was wide enough to swallow it. The tolerance is now 0.001 px and the attack fails as it should.

When it refuses

14 specs in the test corpus are there because they must not render. A squeezed bar chart is the clearest case: the label column and the value column are sized from measured text, and if what is left for the bars falls below the minimum track length, the solver finds a positive cycle in the constraint graph and reports the chain of requirements that contradict each other.

Unsatisfiable: constraints on the x axis cannot all hold. These 8 constraints form a conflicting cycle:
  bar chart 0 value column is flush with the panel's right edge
  bar chart 0 panel content ends at x=164.0
  bar chart 0 panel content starts at x=36.0
  bar chart 0 label column is exactly 31.49px, its widest measured label
  bar chart 0 keeps a 12.0px gap between labels and bars
  bar chart 0 bars need at least 28.0px of track
  bar chart 0 keeps a 12.0px gap between bars and values
  bar chart 0 value column is exactly 314.84px, its widest measured value
